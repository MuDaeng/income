# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

See also `AGENTS.md` (NestJS 12 specifics: first-party packages to prefer, ESM rules, NestJS Observe for production data).

## Commands

- `npm run start` / `npm run start:dev` — run the `api` app (Nest CLI, rspack builder). Listens on `PORT` (default 8080); Swagger UI at `/api-docs` (not served when `NODE_ENV=production`).
- `npm run build` — build to `dist/apps/api`; `npm run start:prod` runs the built output.
- `npm run build:batch` / `npm run start:batch` / `npm run start:batch:dev` / `npm run start:batch:prod` — the `batch` app (daily jobs, no HTTP; `dist/apps/batch`). Run one job now and exit: `node dist/apps/batch/main --run=<exchange-rates|domestic-securities|overseas-securities|us-daily-prices>` (exit code 1 on failure).
- `npm run lint` — oxlint, type-aware. `typescript/no-floating-promises` is an error, so always `await` repository calls.
- `npm test` — Vitest unit tests (`**/*.spec.ts`). Single file: `npx vitest run apps/api/test/balance/balance.service.spec.ts`; single test: add `-t "<name>"`.
  - **Test files never sit next to source.** Each project keeps its tests in `test/` beside `src/`, mirroring the `src/` path: `apps/api/src/balance/balance.service.ts` → `apps/api/test/balance/balance.service.spec.ts`, `libs/core/src/clients/toss/toss.client.ts` → `libs/core/test/clients/toss/toss.client.spec.ts`. Import the code under test relatively through `src` (e.g. `../../src/balance/balance.service.js`); shared code still comes from `@app/common` / `@app/core`.
- `npm run test:e2e` — Vitest with `vitest.config.e2e.ts` (`**/*.e2e-spec.ts`, none yet — passes with no tests). E2E boots the real `ApiModule`, so it needs a reachable MySQL.

If port 8080 is already in use (the user often has a dev server running), start another instance with `PORT=8081` instead of killing the existing process.

## Architecture

Nest monorepo (`nest-cli.json`, `monorepo: true`), ESM throughout (relative imports end in `.js`).

- `apps/api` — the HTTP API. `ApiModule` is the root: it imports `DatabaseModule` and one feature module per business area. Each feature module registers the entities it uses with its own `TypeOrmModule.forFeature([...])` (e.g. `AuthModule` → `[Oauth, User, Token]`).
  - **Each new business area gets its own folder and module** under `apps/api/src/<feature>/` (e.g. `auth/` → `AuthModule` in `auth/auth.module.ts`). That folder's controllers, strategies, services etc. are declared in its module, not in `ApiModule`.
  - **Feature folders follow the entity domains of `libs/common`.** Code working on entities from `libs/common/src/<domain>/` goes in `apps/api/src/<domain>/` and its one module — e.g. `DailySecurity` and `DailyExchangeRate` live in `libs/common/src/security/`, so their controllers/services (`daily-security.*`, `exchange-rate.*`) sit flat in `security/` and are registered in `SecurityModule`. Don't create a separate feature folder per entity.
  - **External API clients go in `libs/core/src/clients/<name>/`** (shared with `batch`), one folder and module per provider (`clients/toss/` → `TossModule`, `clients/massive/` → `MassiveModule`, `clients/data-go-kr/` → `DataGoKrModule`, `clients/kis/` → `KisModule`), each exporting its client and holding its response types in `<name>.types.ts`, all re-exported from `libs/core/src/index.ts`. Feature modules import the client module from `@app/core`.
  - **`ApiModule` only imports the feature module** (`imports: [..., AuthModule]`); don't add a feature's controllers/providers to `ApiModule` directly.
  - **Controllers only call services.** A controller class contains only route handler methods, and each handler just passes request inputs to a service method and returns its result. No private/helper methods, no business logic, no repository or `TokenProvider` access in controllers — put that logic in the service. Need the response? Don't take `@Res()`: return `{ url }` with `@Redirect()`, and set cookies from the service via `RefreshTokenContext.setRefreshTokenCookie`.
- `apps/batch` — daily jobs app (`NestFactory.createApplicationContext`, no HTTP). `BatchModule` imports `DatabaseModule`, `ScheduleModule.forRoot()` (`@nestjs/schedule`) and the `@app/core` import modules; `BatchJobs` (`batch.jobs.ts`) holds the `@Cron` jobs, all `timeZone: 'Asia/Seoul'`, `waitForCompletion`: 16:00 USD/KRW rates (`ExchangeRateService.importFromMassive` for the last 7 days, so missed days self-heal), 17:00 domestic listings (`importFromToss(DOMESTIC_MARKETS)` = KOSPI·KOSDAQ), 08:00 overseas listings (`importFromToss(OVERSEAS_MARKETS)` = NYSE·NASDAQ·AMEX), 15:00 US daily prices (`UsDailyPriceImportService.importFromMassive` for the 7 days up to yesterday in America/New_York; one Massive call per weekday, ~30 s). Massive Basic only serves a day's data after midnight US Eastern — earlier requests get 403 "before end of day", which `MassiveClient` throws as `MassiveDataNotReadyException`; the import then stops at that date and returns what it saved instead of failing. A failed job is logged and returns false; the process keeps running. On startup it logs each job's next run. Domestic daily prices and all dividends are not batched — they are fetched online by the query APIs (`SecurityRefreshService`, see KIS Open API).
- `libs/core` — code shared by `api` and `batch`, imported as `@app/core`: the external API clients and the import services — `SecurityImportService` (`SecurityImportModule`, batch only), `ExchangeRateService` (`ExchangeRateImportModule`) and `UsDailyPriceImportService` (`UsDailyPriceImportModule`). All three are batch only: **the api app has no import (bulk data collection) endpoints** — they were removed because any Google account could trigger unbounded external API calls. To backfill, run a batch job with `--run=`. In api, domestic prices and all dividends arrive only through `SecurityRefreshService` (see KIS Open API).
- `libs/common` — shared library, imported as `@app/common` (path alias in `tsconfig.json`, resolved in Vitest via `resolve.tsconfigPaths`). Holds:
  - `DatabaseModule`: global `ConfigModule` (loads `.env` + `dbConfig` from `config/db.config.ts`) and `TypeOrmModule.forRootAsync` for MySQL (`mysql2`) with `synchronize: true`, `autoLoadEntities: true` and `timezone: '+09:00'`. The MySQL server must run with `time_zone = +09:00` too (`default-time-zone`; RDS: parameter group `Asia/Seoul`): `createdAt`/`updatedAt` are `TIMESTAMP`s filled by MySQL, shown in the session time zone, and mysql2 parses them with this option — change both together or times shift by 9 hours.
  - TypeORM entities grouped by domain (`user/`, `auth/`) with `BaseTimeEntity` (abstract, `createdAt`/`updatedAt`, no `@Entity`) as a base class.
  - Each folder has an `index.ts` barrel re-exported from `libs/common/src/index.ts`; import entities from `@app/common`.

### Decorators

**Request inputs in controllers come only from parameter decorators — never `@Req()` / `@Res()`.**

- Body/params/query: Nest's `@Body()`, `@Param()`, `@Query()`.
- **Validate request input with a Zod schema on the decorator:** `@Body({ schema: xSchema }) body: XRequest` (same for `@Param`/`@Query`). The global `StandardSchemaValidationPipe` in `main.ts` runs it and returns 400 with per-field messages; Swagger picks the schema up automatically. Put the schema in `<feature>/<name>.schema.ts` and export its type with `z.infer` (e.g. `balance/register-balance.schema.ts`). Decimal inputs are strings (`/^d+(.d+)?$/`); in Zod 4 a `refine` still runs after a failed `regex`, so guard it before calling `new Decimal(value)` or invalid input turns into a 500. E2E tests that build the app without `main.ts` must add `app.useGlobalPipes(new StandardSchemaValidationPipe())` themselves.
- Authenticated user: a custom param decorator that matches the route's guard. Using the decorator without its guard gives `undefined`.

  | Guard on the route | Decorator | Value |
  |---|---|---|
  | `@UseGuards(AuthGuard('jwt'))` (Bearer access token) | `@CurrentUser()` | `AuthUser` (`{ id }`) |
  | `@UseGuards(AuthGuard('google'))` (Google callback) | `@GoogleUser()` | `User` from `GoogleStrategy.validate` |
  | `@UseGuards(RefreshTokenGuard)` (refresh token cookie) | none — the service reads `RefreshTokenContext.getRefreshToken()` / `getSub()` | |

- Responses: return the value; use `@Redirect()` + return `{ url }` for redirects, and `@HttpCode(200)` on `POST` routes that don't create anything (`/auth/access`, `/auth/reissue`).

**New custom param decorators:**

- One per file, `<name>.decorator.ts`, in the feature folder (e.g. `auth/current-user.decorator.ts`); export a `PascalCase` const built with `createParamDecorator`, with an explicit return type.
- Only extract a value from the request (usually what a guard/strategy put on `req.user`). No validation, DB access or other logic — that belongs in the guard/strategy or the service.
- Add a JSDoc line naming the guard it requires.
- When a new guard type needs its user, add a new decorator rather than reusing one with a different shape (that's why `@GoogleUser()` exists alongside `@CurrentUser()`).

**Swagger decorators on every controller/handler:** `@ApiTags('<feature>')` on the controller; `@ApiOperation({ summary: '<Korean description>' })` on each handler; `@ApiBearerAuth()` next to `AuthGuard('jwt')`; `@ApiCookieAuth(REFRESH_TOKEN_COOKIE)` next to `RefreshTokenGuard`.

**Other decorators:** `@Transactional()` only on service methods (see Data access); `@InjectRepository()` only in constructors.

### Entity conventions

- **Column/property names are unprefixed:** `id`, not `userId`; `name`, not `userName`; `email`, not `oauthEmail`. The entity/table already gives the context.
- **Join column naming:** a relation's `@JoinColumn` normally follows the same rule (e.g. `id`). Only when that name would collide with an existing property of the entity that means something different (e.g. the entity has its own `id` and also references `User`), name the join column `<table name> + <property name>` in camelCase — e.g. `@JoinColumn({ name: 'userId' })`.
- **Prices, quantities and money amounts use `@Column(decimalColumn)` with TS type `string`** (`libs/common/src/base/decimal-column.ts`: `DECIMAL(20, 6)`, no transformer — mysql2 returns DECIMAL as a string like `'123.450000'`). Don't use plain `@Column()` (`int`), and never convert them to `number`.
  - **Do all arithmetic with decimal.js** (`import { Decimal } from 'decimal.js'` — the default import doesn't type-check under NodeNext). Accept inputs as `Decimal.Value`.
  - **Before saving, truncate by the security's currency with `truncateByCurrency(value, security.currency)`** (`libs/common/src/security/currency-decimal.ts`): `KRW` (domestic stocks/bonds) → integer, `USD` (overseas) → 6 decimal places, always `ROUND_DOWN`. This applies to both money and quantities. Look the `Security` up in the service to get its currency (see `BalanceService.registerBalance`).
- **Enum columns need `@Column({ type: 'enum', enum: X })`** — a bare `@Column()` on an enum-typed property fails at startup with `Data type "undefined" ... is not supported`.
- **Composite-FK join columns must name their target:** `@JoinColumn([{ name: 'userId', referencedColumnName: 'userId' }, { name: 'securityId', referencedColumnName: 'securityId' }])`. Without `referencedColumnName`, TypeORM mapped both to `userId` (`FOREIGN KEY (userId, userId)`, then `Duplicate column name`).
- **Relations are unidirectional by default.** Declare the relation only on the owning side (the side with the `@JoinColumn`, usually `@ManyToOne`/`@OneToOne`) and omit the inverse `@OneToMany`/inverse-side callback. Add a bidirectional relation only when it is truly unavoidable, and note why in a comment.

### Data access: Repository only

- **All CRUD goes through TypeORM `Repository`**, using its methods (`find*`, `save`, `insert`, `update`, `delete`, ...).
- **Repositories are obtained only by constructor injection with `@InjectRepository`:**
  ```ts
  constructor(
    @InjectRepository(User)
    private readonly userRepository: Repository<User>,
  ) {}
  ```
  The entity must be in a `TypeOrmModule.forFeature([...])` imported by that feature's module. Don't get repositories any other way (`dataSource.getRepository(...)`, `manager.getRepository(...)`, custom repository classes).
- Don't do CRUD via `EntityManager` methods (`manager.save(Entity, ...)`, `dataSource.manager.*`), `createQueryBuilder`, or raw `query()`.
- **Transactions use `@Transactional()` from `typeorm-transactional`** on a service method; injected repositories automatically join the transaction, and a thrown error rolls everything back. Don't use `dataSource.transaction(...)` or `QueryRunner`. Setup (already done): `initializeTransactionalContext()` in `main.ts` before `NestFactory.create`, and `addTransactionalDataSource` in `DatabaseModule`'s `dataSourceFactory`. Tests that call a `@Transactional()` method against a real DB must call `initializeTransactionalContext()` first.

### TypeORM gotchas in this setup

- `autoLoadEntities` only loads entities passed to some `forFeature()`. Every entity on either side of a relation must be registered, or startup fails with `Entity metadata for X#y was not found`.
- `synchronize: true` alters the live DB schema on every boot from entity definitions — entity changes are schema changes.
- **Per-group sequence numbers (max + 1) are assigned in the service, not in entity listeners** (`@BeforeInsert` has no DI and would need a global DataSource + QueryBuilder). In a `@Transactional()` method, first lock the owning parent row by PK (e.g. `userRepository.findOne({ where: { id }, lock: { mode: 'pessimistic_write' } })`), then read the group's last row with `findOne({ order: { sequence: 'DESC' } })` and save with `+ 1`. Don't put the lock on the sequence table's own range query: InnoDB gap locks make concurrent inserts deadlock (verified — 2 of 5 concurrent saves failed even with 3 retries). A PK lookup on the parent takes a plain record lock, so same-owner saves run one at a time with no deadlock (verified with 10 concurrent saves). See `BalanceService.registerBalance`.
- `Oauth → User` is a unidirectional `@ManyToOne` (`User` has no `oauth` property), so there is no cascade from `User`. Save the `User` first (`userRepository.save`), then save `Oauth` with `user` set (`oauthRepository.save`), in one `@Transactional()` method (see `AuthService.findOrCreateOauthUser`). `Oauth` has a composite PK (`id` = the user's id, doubling as the `@JoinColumn` to `User`, + `type` enum).

## Environment

`.env` (not committed) supplies `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`, `PORT`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `API_URL` (the API's public origin, e.g. `http://localhost:8080` locally, `https://api.mudaeng.online` in production) + `GOOGLE_CALLBACK_URI` (path only, `/auth/google/callback`; the Google callback URL is `API_URL + GOOGLE_CALLBACK_URI` and must be registered in Google Cloud Console), `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET` (must differ), `JWT_ACCESS_EXPIRES_IN` / `JWT_REFRESH_EXPIRES_IN` (seconds), `FRONTEND_URL1` / `FRONTEND_URL2` (CORS origins, e.g. `https://www.mudaeng.online` / `https://mudaeng.online`; `FRONTEND_URL1` is also the post-login redirect target), `NODE_ENV` (`production` disables Swagger and makes the refresh cookie `secure`), `HOST` (listen address, default `127.0.0.1`; production runs behind Nginx with `PORT=3000`), `TOSS_CLIENT_ID` / `TOSS_CLIENT_SECRET` (Toss Open API; the calling machine's IP must be on Toss's allowed-IP list, otherwise 403), `MASSIVE_API_KEY` (Massive REST API, sent as `Authorization: Bearer`), `DATA_GO_KR_SERVICE_KEY` (data.go.kr decoding key, sent as the `serviceKey` query param), `KIS_CLIENT_ID` / `KIS_CLIENT_SECRET` (Korea Investment & Securities Open API appkey/appsecret).

### Toss Open API

Call Toss only through `TossClient` (`libs/core/src/clients/toss/toss.client.ts`, exported by `TossModule`). It caches the access token in memory until shortly before expiry: Toss allows one valid token per client, so issuing a new one revokes the previous token — never request a token per call. If another process (e.g. a `--run` batch next to the scheduled one) issues a token, a `listStocks` 401 drops the cached token and retries once with a new one. `GET /api/v1/stocks/all` is rate-limited to 1 request/second (the import waits between markets). Only the batch calls Toss: its `domestic-securities` / `overseas-securities` jobs (or `--run=` either) call `SecurityImportService.importFromToss(markets)`, which upserts the markets' listings into `Security` (`id` = ISIN, currency from the market). The api app has no `POST /securities/import` any more.

### Massive API

Call Massive only through `MassiveClient` (`libs/core/src/clients/massive/massive.client.ts`, exported by `MassiveModule`). `ExchangeRateService.importFromMassive` (`@app/core`, input `{ from?, to? }`, default the last 2 years; the batch's `exchange-rates` job) fetches `C:USDKRW` daily bars and upserts them into `DailyExchangeRate` as `currency = USD` (KRW per USD; `date` = the bar's UTC date). Rates keep 6 decimals (`ROUND_DOWN`) — don't use `truncateByCurrency` on them, KRW would cut them to integers. The Currencies Basic plan only serves 2 years of end-of-day data.

`UsDailyPriceImportService.importFromMassive` (`@app/core`, same input; the batch's daily `us-daily-prices` job) calls the Daily Market Summary (`/v2/aggs/grouped/locale/us/market/stocks/{date}`) once per weekday — one call returns every US ticker for that day, holidays return no results — and upserts the bars into `DailySecurity` for `USD` securities, matched by `Security.symbol` (Toss preferred-share symbols `BAC-P` become Massive `BACpP`; unknown tickers are skipped; the conversion is `toMassiveTicker` in `libs/core/src/clients/massive/massive-ticker.ts`). Prices use `truncateByCurrency(USD)`.

Security lookup is split in two public (no JWT) routes, because a name can equal another security's symbol (e.g. `SK`): `GET /securities?keyword` (`SecurityService.searchSecurities`) finds securities by exact `symbol`, then exact `name`, then partial `name` (`Like`, `%`/`_`/`\` escaped) — never by ISIN — capped at 20, each with its latest stored closing price (null if none); `GET /daily-securities?securityId&from&to` (`DailySecurityService.getDailyPrices`) then refreshes that security online (`SecurityRefreshService.refresh`) and reads the daily bars for that exact ISIN (none → 404). `from`/`to` are optional and inclusive; prices are truncated by the security's currency.

**Purchase exchange rate:** `PurchaseDateBalance.exchangeRate` (nullable, KRW per USD, 6 decimals `ROUND_DOWN` — not `truncateByCurrency`) is the rate the user actually paid. `POST /balance` takes an optional `exchangeRate`: `KRW` securities always store null (input ignored); others store the input, else the latest USD `closingRate` on or before `purchaseDate`, else null (registration still succeeds). `POST /balance/sale` copies it to a split-off sold row and only merges into a sold row with the same `price` **and** `exchangeRate`. Every KRW conversion of a USD purchase cost — `GET /balance` (`krwPurchaseAmount`/`krwAveragePrice`), `GET /balance/purchases`, `GET /balance/returns` — uses the stored rate, falling back to the latest USD rate on or before `purchaseDate` (none → 404 in `/balance` and `/balance/returns`). `PATCH /balance/purchases` (JWT, `BalanceService.updateExchangeRate`, body `{ securityId, purchaseDate, sequence, exchangeRate }`) changes one row's stored rate (sold rows too; `exchangeRate: null` clears it so queries fall back again — the key is required, omitting it is 400); no row → 404, `KRW` security → 400. Evaluation amounts still use the latest rate (`/balance`) or the rate on or before `to` (`/balance/returns`), so FX gains are in the KRW totals.

`GET /balance/purchases?securityId` (JWT, `BalanceService.getPurchases`) lists the user's `PurchaseDateBalance` rows for one security, newest `purchaseDate` first (then `sequence` desc), sold rows included, with the purchase exchange rate (stored rate with `exchangeRateDate` null, else the fallback rate and its date; null for KRW). `price` is cut to 2 decimals (`ROUND_DOWN`) in the response.

`DELETE /balance/purchases?securityId&purchaseDate&sequence` (JWT, 204, `BalanceService.deletePurchase`) deletes one mis-registered `PurchaseDateBalance` row of the user (sold rows too; none → 404). `sequence` is only unique within a `purchaseDate`, so all three are required. When the security has no rows left, its `UserBalance` is deleted too. Other rows' sequences are not renumbered.

`MassiveClient.getDividends(ticker, fromExDate, toExDate)` reads `/stocks/v1/dividends` (cash dividends, filtered by ex-dividend date, `limit=5000`, follows `next_url`). `DividendService` uses it for `USD` securities (see KIS Open API below). `MassiveClient` retries a 429 after `Retry-After` (default 15s), so a rate-limited plan just runs slower.

### data.go.kr

Call data.go.kr only through `DataGoKrClient` (`libs/core/src/clients/data-go-kr/data-go-kr.client.ts`, exported by `DataGoKrModule`). `getStockPrices` (FSC stock price API `getStockPriceInfo_V2`, domestic listed stocks only) and `getEtfPrices` (FSC securities product price API `GetSecuritiesProductInfoService_V2/getETFPriceInfo_V2`; the stock API has no ETFs) share the query and response shape through `getPricePage`. Today only `DailyPriceFetcher` uses them, filtered by `isinCd` for one security (see Online refresh). `endBasDt` is exclusive, so callers pass `to + 1 day`. Errors such as an unregistered key come back as `OpenAPI_ServiceResponse` (or XML) instead of `response.header`, and the client turns them into 502. The data.go.kr key needs a separate 활용신청 for 증권상품시세정보 for ETFs; otherwise the call returns `SERVICE_KEY_IS_NOT_REGISTERED_ERROR`.

### KIS Open API

Call KIS (한국투자증권, `https://openapi.koreainvestment.com:9443`) only through `KisClient` (`libs/core/src/clients/kis/kis.client.ts`, exported by `KisModule`). The access token (`POST /oauth2/tokenP`) is stored in `ClientToken` (`clientType = KIS`; `token` is `text` because the JWT is longer than 255 chars) and reused across calls and restarts — never issue one per call. `KisClient` issues a token only when none is stored, or once when a call returns 401 (KIS may also report an expired token as HTTP 500 with `msg_cd` `EGW00121`/`EGW00123`), saves it, and retries that call once.

Dividends for `KRW` securities come from the KSD dividend schedule (`GET /uapi/domestic-stock/v1/ksdinfo/dividend`, `tr_id` `HHKDB669102C0`, per 6-digit `Security.symbol`); `USD` securities use Massive Dividends with `toMassiveTicker(symbol)` (amount `truncateByCurrency(USD)`, `noticeDate` = record date, or ex-dividend date if missing). `DividendService.fetchAndSave(security, from, to)` (`security/dividend.service.ts`) upserts `Dividend` (cash → `MONEY`; KIS stock dividends → `STOCK`, rate in %; rows without a payment date are skipped since it is part of the PK).

**Online refresh:** `SecurityRefreshService.refresh(security)` (`security/security-refresh.service.ts`, the only export of `SecurityModule`) is how query APIs get fresh data — call it, never the clients or `DividendService` directly. At most once a day per security **and kind**: `SecuritySearch` has a composite PK (`id`, `type`: `SearchType.INCOME` = dividends, `SearchType.PRICE` = daily prices), each row with its own `lastSearchDate`. A kind whose row is today (Asia/Seoul) is skipped; otherwise dividends fetch 2 years back → 1 year ahead, and — `KRW` only — daily prices 2 years back → today. `KRW` prices come from `DailyPriceFetcher` (`security/daily-price.fetcher.ts`): data.go.kr filtered by `isinCd` (ETF type → ETF API, else stock API). `USD` prices are never fetched online — the batch's `us-daily-prices` job loads every US ticker daily — so a `USD` refresh is one Massive dividends call and has no `PRICE` row. Each kind's row is upserted (`['id', 'type']`) only when that kind succeeds; a failure is logged, never thrown, so the caller answers from stored data and the next call retries just that kind. Other currencies are ignored. Callers: `GET /daily-securities`, `GET /balance/dividends` (each held security, sequentially — Massive rate limits can make a first call of the day slow with many USD securities; `/balance/returns` gets it through `DividendHistoryService`), and `BalanceService.registerBalance` (only after the `saveBalance` transaction has committed, so a failed registration never calls external APIs). KIS issues at most one token per minute (`EGW00133`). Reuse it for future security lookup APIs instead of calling `KisClient` directly.

### Dividend history

`GET /balance/dividends?from&to` (`DividendHistoryService.getDividendHistory`, `balance/dividend-history.*`) first refreshes each security the user has held (`SecurityRefreshService.refresh`), then reads stored `Dividend` rows. Rules: cash dividends (`MONEY`) only; `from`/`to` filter `paymentDate` (inclusive; omitted = unbounded, so announced future payments are included) and months group by payment month; quantity = sum of the user's `PurchaseDateBalance` rows (sold ones included) with `purchaseDate <= noticeDate` and (`saleDate` null or `> noticeDate`), rows with quantity 0 are dropped; amount = per-share × quantity, `truncateByCurrency`. USD converts with the latest USD `closingRate` on or before `paymentDate` (`krwAmount` null and left out of the sums if none). Monthly/total sums add the truncated per-row values.

`GET /balance/returns?from&to` (both required; `PeriodReturnService`, `balance/period-return.*`) values the positions held on `to` (`purchaseDate <= to`, `saleDate` null or `> to`; sale prices aren't stored, so sold positions only count through their dividends) at the latest closing price on or before `to`, and adds dividends from `DividendHistoryService` for the same `from`/`to`. USD cost in KRW uses each purchase's own rate (the stored purchase exchange rate, else the latest USD rate on or before `purchaseDate`, so FX gains are in the KRW return); USD evaluation uses the latest rate on or before `to`. Securities = held on `to` ∪ paid a dividend in the period. `returnRate` lives in `balance/return-rate.ts` (shared with `BalanceService`).

### Auth flow

1. `GET /auth/google` → Google → `GET /auth/google/callback`: the handler takes the Google user with `@GoogleUser()` (`auth/google-user.decorator.ts`, the `User` returned by `GoogleStrategy.validate`) and `AuthService.loginWithOauth` saves both tokens in `Token` (one row per user, PK `id` = user id), sets the refresh token as an httpOnly `refreshToken` cookie (`path: /auth`), and returns `{ url: ${FRONTEND_URL1}/auth/callback }` for `@Redirect()`.
2. Frontend calls `POST /auth/access` with credentials: `AuthService.issueAccessToken` looks the refresh token up in `Token` and returns a new access token in the body (also stored in `Token`); the refresh token is unchanged.
3. Frontend sends `Authorization: Bearer <accessToken>`; protect routes with `@UseGuards(AuthGuard('jwt'))` (`JwtStrategy`, access secret) and take the user with the `@CurrentUser()` param decorator (`auth/current-user.decorator.ts`, gives `AuthUser` = `{ id }`) instead of `@Req()`, passing it to the service (e.g. `GET /auth/me` → `AuthService.getMe`). An expired access token gets 401.
4. On 401, frontend calls `POST /auth/reissue` with credentials: `AuthService.reissueTokens` looks the refresh token up in `Token` (missing → 401), deletes the old row, issues and saves a new access + refresh pair, resets the `refreshToken` cookie, and returns `{ accessToken }`. The old refresh token is unusable afterwards (rotation).

**Refresh-token context** (`auth/refresh-token.context.ts`, holding `RefreshTokenContext` + `RefreshTokenContextMiddleware` because the middleware must open the file-private `AsyncLocalStorage`): the middleware opens a per-request store (applied to all routes in `AuthModule.configure`). `@UseGuards(RefreshTokenGuard)` (`auth/refresh-token.guard.ts`) reads the `refreshToken` cookie, verifies it (missing/expired/invalid → 401), and stores the token and its `sub` (user id). Services then read them with `RefreshTokenContext.getRefreshToken()` / `getSub()` instead of taking them as parameters, and set the cookie with `RefreshTokenContext.setRefreshTokenCookie(token)`. `AuthModule` exports `RefreshTokenContext` and `RefreshTokenGuard` for other feature modules.

**Keep `/auth/access` and `/auth/reissue` as separate endpoints** — don't merge them or remove `/auth/access`. `/auth/access` is only for right after login (new access token, refresh token unchanged); `/auth/reissue` is for an expired access token (both tokens rotated).

**Rate limiting** (`@nestjs/throttler`): `ApiModule` registers `ThrottlerModule.forRoot(THROTTLER_OPTIONS)` and a global `ThrottlerGuard` (APP_GUARD — infrastructure like `DatabaseModule`, so it sits in `ApiModule`). Limits live in `apps/api/src/rate-limit.ts`: 100 req/min per IP by default, `@Throttle(AUTH_THROTTLE)` (10/min) on `/auth/google`, `/auth/google/callback`, `/auth/access`, `/auth/reissue`, `@Throttle(PRICE_THROTTLE)` (30/min) on `GET /daily-securities` (public and triggers external refreshes). Over the limit → 429. The tracker is `req.ip`, which is the real client IP only because of `trust proxy 1` in `main.ts`. Storage is in memory (one pm2 process).

**Google OAuth state** (login CSRF protection): `GoogleStrategy` passes `store: new OAuthStateStore()` (`auth/oauth-state.store.ts`). There is no express-session, so the state goes in an httpOnly `oauthState` cookie (`path: /auth/google`, 10 min, SameSite=Lax so it rides the top-level redirect back from Google); `verify` compares it with the `state` query in constant time and clears it, mismatch → 401. passport picks the call shape by method arity, so keep `store(req, cb)` at 2 and `verify(req, state, cb)` at 3 parameters (hence the `as unknown as StateStore` cast).

JWTs are signed only through `TokenProvider` (`auth/token.provider.ts`), which passes the access/refresh secret per call (`JwtModule.register({})` has no default secret). A Google OAuth `client_secret_*.json` sits untracked at the repo root — never commit it.
