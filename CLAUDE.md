# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

See also `AGENTS.md` (NestJS 12 specifics: first-party packages to prefer, ESM rules, NestJS Observe for production data).

## Commands

- `npm run start` / `npm run start:dev` — run the `api` app (Nest CLI, rspack builder). Listens on `PORT` (default 8080); Swagger UI at `/api-docs` (not served when `NODE_ENV=production`).
- `npm run build` — build to `dist/apps/api`; `npm run start:prod` runs the built output.
- `npm run build:batch` / `npm run start:batch` / `npm run start:batch:dev` / `npm run start:batch:prod` — the `batch` app (daily jobs, no HTTP; `dist/apps/batch`). Run one job now and exit: `node dist/apps/batch/main --run=<exchange-rates|domestic-securities|overseas-securities|us-daily-prices|domestic-daily-prices|expired-tokens>` (exit code 1 on failure).
- `npm run lint` — oxlint, type-aware. `typescript/no-floating-promises` is an error, so always `await` repository calls.
- `npm test` — Vitest unit tests (`**/*.spec.ts`). Single file: `npx vitest run apps/api/test/balance/restapi/balance.service.spec.ts`; single test: add `-t "<name>"`.
  - **Test files never sit next to source.** Each project keeps its tests in `test/` beside `src/`, mirroring the `src/` path: `apps/api/src/balance/restapi/balance.service.ts` → `apps/api/test/balance/restapi/balance.service.spec.ts`, `libs/common/src/client/toss/toss.client.ts` → `libs/common/test/client/toss/toss.client.spec.ts`. Import the code under test relatively through `src` (e.g. `../../../src/balance/restapi/balance.service.js`); shared code still comes from `@app/common`.
- `npm run test:e2e` — Vitest with `vitest.config.e2e.ts` (`**/*.e2e-spec.ts`, none yet — passes with no tests). E2E boots the real `ApiModule`, so it needs a reachable MySQL.

If port 8080 is already in use (the user often has a dev server running), start another instance with `PORT=8081` instead of killing the existing process.

## Architecture

Nest monorepo (`nest-cli.json`, `monorepo: true`), ESM throughout (relative imports end in `.js`).

- `apps/api` — the HTTP API. `ApiModule` is the root: it imports `DatabaseModule` and one feature module per business area. Each feature module registers the entities it uses with its own `TypeOrmModule.forFeature([...])` (e.g. `AuthModule` → `[Oauth, User, Token]`).
  - **Each new business area gets its own folder and module** under `apps/api/src/<feature>/` (e.g. `auth/` → `AuthModule` in `auth/auth.module.ts`). That folder's controllers, strategies, services etc. are declared in its module, not in `ApiModule`.
  - **Inside a feature folder, the HTTP entry layer lives in `restapi/`:** controllers, services, and (in `auth/`) guards, strategies, param decorators, `refresh-token.context.ts` and `oauth-state.store.ts`, plus the request/response `restapi/dto/` folder. The feature root keeps only `<feature>.module.ts`, the implementation layer (Reader/Writer/Fetcher/Refresher/Calculator, see Layers) and plain helpers (`return-rate.ts`, `money.ts`, `account-amount.ts`, `toss-lending.ts`, `price-date.ts`). E.g. `balance/balance.module.ts`, `balance/purchase.writer.ts`, `balance/restapi/balance.controller.ts`, `balance/restapi/dto/register-balance.schema.ts`.
  - **Feature folders follow the entity domains of `libs/common`.** Code working on entities from `libs/common/src/<domain>/` goes in `apps/api/src/<domain>/` and its one module — e.g. `DailySecurity` and `DailyExchangeRate` live in `libs/common/src/security/`, so their controllers/services (`daily-security.*`, `exchange-rate.*`) sit flat in `security/` and are registered in `SecurityModule`. Don't create a separate feature folder per entity.
  - **External API clients go in `libs/common/src/client/<name>/`** (shared with `batch`), one folder and module per provider (`client/toss/` → `TossModule`, `client/massive/` → `MassiveModule`, `client/data-go-kr/` → `DataGoKrModule`, `client/kis/` → `KisModule`; `client/` also holds the `ClientToken` entity), each exporting its client and holding its response types in `<name>.types.ts`, all exported from `libs/common/src/client/index.ts`. Feature modules import the client module from `@app/common`.
  - **`ApiModule` only imports the feature module** (`imports: [..., AuthModule]`); don't add a feature's controllers/providers to `ApiModule` directly.
  - **Controllers only call services.** A controller class contains only route handler methods, and each handler just passes request inputs to a service method and returns its result. No private/helper methods, no business logic, no repository or `TokenProvider` access in controllers — put that logic in the service. Need the response? Don't take `@Res()`: return `{ url }` with `@Redirect()`, and set cookies from the service via `RefreshTokenContext.setRefreshTokenCookie`.
- `apps/batch` — daily jobs app (`NestFactory.createApplicationContext`, no HTTP). `BatchModule` imports `DatabaseModule`, `ScheduleModule.forRoot()` (`@nestjs/schedule`) and the `@app/common` modules (`SecurityImportModule`, `TokenModule`, `BatchHistoryModule`). Like api's `restapi/`, the cron entry layer lives in `apps/batch/src/scheduler/`: `BatchJobs` (`scheduler/batch.jobs.ts`) holds the `@Cron` jobs (the app root keeps only `main.ts` and `batch.module.ts`), all `timeZone: 'Asia/Seoul'`, `waitForCompletion`: 16:00 USD/KRW rates (`ExchangeRateFetcher.importFromMassive` for the last 7 days, so missed days self-heal), 17:00 domestic listings (`importFromToss(DOMESTIC_MARKETS)` = KOSPI·KOSDAQ), 08:00 overseas listings (`importFromToss(OVERSEAS_MARKETS)` = NYSE·NASDAQ·AMEX), 14:30 US daily prices (`UsDailyPriceFetcher.importFromMassive` for the 7 days up to yesterday in America/New_York = the trading day that just closed; 14:30 KST is 00:30 ET, 01:30 in US summer time; one Massive call per weekday, ~30 s). Massive Basic only serves a day's data after midnight US Eastern (13:00/14:00 KST), so don't schedule it earlier — earlier requests get 403 "before end of day", which `MassiveClient` throws as `MassiveDataNotReadyException`; the import then stops at that date and returns what it saved instead of failing. 13:30 domestic stock + ETF daily prices (`DomesticDailyPriceFetcher.importFromDataGoKr`, `libs/common/src/security/domestic-daily-price.fetcher.ts`, today − 4 days → today KST; data.go.kr publishes a business day late, so the latest bar is usually the previous business day; ~3 s): stock API then ETF API, 10,000-row pages, ranges split by calendar month, only ISINs of `KRW` securities saved. 00:00 expired login sessions (`TokenProvider.deleteExpiredRefreshTokens`, `TokenModule` in `libs/common/src/auth/`): deletes every `Token` row whose `updatedAt` is older than `JWT_REFRESH_EXPIRES_IN` — each issue/reissue updates the row, so its refresh token has expired (`AuthService.loginWithOauth` also prunes the logging-in user's expired rows). A failed job is logged and returns false; the process keeps running. Every run (cron or `--run=`) is also recorded in `BatchHistory` (`libs/common/src/batch/`, table `batch_history`) by `BatchHistoryWriter` (`libs/common/src/batch/batch-history.writer.ts`, from `BatchHistoryModule`): `start` saves a `RUNNING` row, `finish` sets `SUCCESS` (result JSON) or `FAILED` (error message, cut to 10,000 chars), `finishedAt`, `durationMs`; a row left `RUNNING` means the process died mid-run. History save errors are only logged, never fail the job. pm2 logs are flushed on every deploy, so check history in MySQL: `SELECT * FROM batch_history WHERE name = 'us-daily-prices' ORDER BY startedAt DESC LIMIT 10;` On startup it logs each job's next run. Dividends are not batched — they are fetched online by the query APIs (`SecurityRefresher`, see KIS Open API), which also fill in one day of domestic prices from KIS.
- `libs/common` also holds the code shared by `api` and `batch` (formerly a separate `libs/core`): the external API clients (`client/`), `TokenModule`/`TokenProvider` (`auth/`, JWT issue/verify for api + expired-session cleanup for batch) and the bulk import fetchers in `security/` — `SecurityFetcher`, `ExchangeRateFetcher`, `UsDailyPriceFetcher` and `DomesticDailyPriceFetcher`, all provided by one `SecurityImportModule` (`security/security-import.module.ts`). They are batch only: **the api app has no public import (bulk data collection) endpoints** — they were removed because any Google account could trigger unbounded external API calls. To backfill, run a batch job with `--run=`. In api, all dividends and the one-day domestic price top-up arrive only through `SecurityRefresher` (see KIS Open API).
- `libs/common` — shared library, imported as `@app/common` (path alias in `tsconfig.json`, resolved in Vitest via `resolve.tsconfigPaths`). Holds:
  - `DatabaseModule`: global `ConfigModule` (loads `.env` + `dbConfig` from `config/db.config.ts`) and `TypeOrmModule.forRootAsync` for MySQL (`mysql2`) with `synchronize: true`, `autoLoadEntities: true` and `timezone: '+09:00'`. The MySQL server must run with `time_zone = +09:00` too (`default-time-zone`; RDS: parameter group `Asia/Seoul`): `createdAt`/`updatedAt` are `TIMESTAMP`s filled by MySQL, shown in the session time zone, and mysql2 parses them with this option — change both together or times shift by 9 hours.
  - TypeORM entities grouped by domain (`user/`, `auth/`) with `BaseTimeEntity` (abstract, `createdAt`/`updatedAt`, no `@Entity`) as a base class.
  - **Shared helpers — reuse them, don't copy them into a file:** `base/iso-date.ts` ('YYYY-MM-DD' math: `addDays`, `addYears`, `formatIsoDate`, `parseIsoDate`, `nextMonthFirst`, `isWeekend`, `toYmd`/`fromYmd`, `todayIn(timeZone)`, `todayInSeoul`, `krwPriceDate`), `base/sleep.ts`, `base/upsert-in-chunks.ts` (`upsertInChunks(repository, rows, conflictPaths)`, 1,000 rows per `upsert`), and in `security/`: `currency-decimal.ts` (`truncateByCurrency`; `toKrw`/`toUsd` = `truncateByCurrency(value, KRW/USD)` for computed amounts; `truncateRate` = 6 decimals for exchange rates/percent rates; `parseKrwPrice` = source price string → KRW integer, empty → 0 — `toKrw('')` throws instead) and `isSupportedCurrency` (`currency.enum.ts`, the KRW·USD set the balance calculations handle). In api, `balance/money.ts` has `sumDecimals` (null skipped) and `security/price-date.ts` has `priceLookupDate(currency, date)` (the last close date to look up: USD date − 1, KRW capped at `krwPriceDate()`).
  - **Barrels (`index.ts`) follow the modules, never the top-level `libs/common/src/index.ts` alone:**
    - **A folder with a `*.module.ts` gets its own `index.ts`** listing every file in that folder (e.g. `client/massive/` has `MassiveModule` → `client/massive/index.ts` exports `massive.client`, `massive.module`, `massive.types`, `massive-ticker`).
    - That barrel is registered in the `index.ts` of the nearest ancestor folder that has one, checked recursively: a folder that holds only subfolders gets no `index.ts`, so its children register one level further up. E.g. `client/index.ts` → `./massive/index.js`, and `src/index.ts` → `./client/index.js`.
    - **Files in a folder without a module** go in the `index.ts` of the top-level folder directly under `src/` that contains them (e.g. `config/` has no module → `config/index.ts`; `client/client-token.entity.ts` → `client/index.ts`).
    - The top-level `src/index.ts` only re-exports the top-level folder barrels plus root-level files (`common.module.ts`, `database.module.ts`). Import everything from `@app/common`.
  - **Inside `libs/common`, import with relative paths to the file** (e.g. `../../config/kis.config.js`), never `@app/common` or a barrel — the library importing its own barrel creates import cycles.

### Decorators

**Request inputs in controllers come only from parameter decorators — never `@Req()` / `@Res()`.**

- Body/params/query: Nest's `@Body()`, `@Param()`, `@Query()`.
- **Validate request input with a Zod schema on the decorator:** `@Body({ schema: xSchema }) body: XRequest` (same for `@Param`/`@Query`). The global `StandardSchemaValidationPipe` in `main.ts` runs it and returns 400 with per-field messages; Swagger picks the schema up automatically. Put the schema in `<feature>/restapi/dto/<name>.schema.ts` and export its type with `z.infer` (e.g. `balance/restapi/dto/register-balance.schema.ts`). **Request schemas (`*.schema.ts`) and response types (`*.dto.ts`) live together in the feature's `restapi/dto/` folder** (`apps/api/src/<feature>/restapi/dto/`), never next to the services; their tests mirror it (`apps/api/test/<feature>/restapi/dto/*.schema.spec.ts`). Decimal inputs are strings (`/^d+(.d+)?$/`); in Zod 4 a `refine` still runs after a failed `regex`, so guard it before calling `new Decimal(value)` or invalid input turns into a 500. E2E tests that build the app without `main.ts` must add `app.useGlobalPipes(new StandardSchemaValidationPipe())` themselves.
- **Date-range query params (`from`/`to`, 'YYYY-MM-DD') — every new and changed endpoint follows this policy** (`GET /balance/dividends`, `/balance/returns`, `/daily-securities`):
  - Both **optional**, both inclusive: `from: z.iso.date().optional()`, `to: z.iso.date().optional()`.
  - Order check on the object with the shared helper: `.refine(isOrderedDateRange, DATE_RANGE_ERROR)` (`libs/common/src/base/date-range.ts`, from `@app/common`) — it only compares when both are present and valid ('YYYY-MM-DD' compares as strings), and the error is '시작일은 종료일과 같거나 이전이어야 합니다.' on path `['from']`. Don't write a local `ISO_DATE` regex or refine.
  - Omitted = unbounded on that side: no `from` = from the beginning, no `to` = to the end (future rows such as scheduled dividends included).
  - When the endpoint needs a concrete date (a valuation date, e.g. `/balance/returns`), an omitted `to` = today (`todayInSeoul()`), and an omitted `from` = the whole history.
  - Response: `from` is `string | null` (the input, null when omitted); `to` is always a `string` — the input, else today (`todayInSeoul()`). On endpoints whose omitted `to` is unbounded (`/balance/dividends`, `/daily-securities`) only the response gets today; the query still has no upper bound, so `/balance/dividends` keeps returning `scheduled` dividends dated after that `to`.
  - Exception: `/balance/monthly` takes required `YYYY-MM` months (≤ 120). Ask the user before making another endpoint deviate from this policy.
- Authenticated user: a custom param decorator that matches the route's guard. Using the decorator without its guard gives `undefined`.

  | Guard on the route | Decorator | Value |
  |---|---|---|
  | `@UseGuards(AuthGuard('jwt'))` (Bearer access token) | `@CurrentUser()` | `AuthUser` (`{ id, rules }`) |
  | `@UseGuards(AuthGuard('google'))` (Google callback) | `@GoogleUser()` | `User` from `GoogleStrategy.validate` |
  | `@UseGuards(RefreshTokenGuard)` (refresh token cookie) | none — the service reads `RefreshTokenContext.getRefreshToken()` / `getSub()` | |

- Responses: return the value; use `@Redirect()` + return `{ url }` for redirects, and `@HttpCode(200)` on `POST` routes that don't create anything (`/auth/access`, `/auth/reissue`).

**New custom param decorators:**

- One per file, `<name>.decorator.ts`, in the feature's `restapi/` folder (e.g. `auth/restapi/current-user.decorator.ts`); export a `PascalCase` const built with `createParamDecorator`, with an explicit return type.
- Only extract a value from the request (usually what a guard/strategy put on `req.user`). No validation, DB access or other logic — that belongs in the guard/strategy or the service.
- Add a JSDoc line naming the guard it requires.
- When a new guard type needs its user, add a new decorator rather than reusing one with a different shape (that's why `@GoogleUser()` exists alongside `@CurrentUser()`).

**Swagger decorators on every controller/handler:** `@ApiTags('<feature>')` on the controller; `@ApiOperation({ summary: '<Korean description>' })` on each handler; `@ApiBearerAuth()` next to `AuthGuard('jwt')`; `@ApiCookieAuth(REFRESH_TOKEN_COOKIE)` next to `RefreshTokenGuard`.

**Other decorators:** `@Transactional()` only on service methods (see Data access); `@InjectRepository()` only in constructors.

### Layers: Controller → Service → implementation layer → Repository / Client

Calls only point down: a controller calls services; a service calls implementation-layer classes (and may use repositories directly for its own logic); the implementation layer calls repositories and `@app/common` clients.

- **A service never injects another service.** Logic that more than one service needs goes into an implementation-layer class instead (e.g. `PeriodReturnService` and `MonthlyBalanceService` use `DividendHistoryCalculator`, not `DividendHistoryService`).
- **The implementation layer never injects a service.** It may inject other implementation-layer classes, one way only.
- Implementation-layer classes are `@Injectable()` and named by role, never `*Service` — file `<name>.<role>.ts`, class `<Name><Role>`:

  | Role | Does | Examples |
  |---|---|---|
  | `Reader` | Repository reads only. `find*` returns null/empty when missing, `get*` throws | `DailyPriceReader`, `ExchangeRateReader` (`security/`), `PurchaseReader`, `PurchaseRateReader` (`balance/`), `AccountReader` (`user/`) |
  | `Writer` | Repository saves/updates/deletes, called inside the service's `@Transactional()` method | `PurchaseWriter` (`balance/`: `lockOwner`, `append`, `sell`, `sellLifo`, `update`, `moveAccount`, `remove`, `removeByAccount`), `AccountWriter` (`user/`: `lockOwner`, `create`, `resolve`, `updateType`, `remove`) |
  | `Fetcher` | Fetches from an external client and saves | `DailyPriceFetcher`, `DividendFetcher` (api); `SecurityFetcher`, `ExchangeRateFetcher`, `UsDailyPriceFetcher`, `DomesticDailyPriceFetcher` (`libs/common`, batch) |
  | `Refresher` | Decides when to run fetchers | `SecurityRefresher` |
  | `Calculator` | Builds a computed result from readers | `DividendHistoryCalculator` |

- They live in the entity-domain feature folder (`security/`, `balance/`) and are registered in that module's `providers`. **Other modules get only implementation-layer classes** in `exports` (`SecurityModule` exports `SecurityRefresher`, `DailyPriceReader`, `ExchangeRateReader`); services are never exported.
- `@Transactional()` stays on service methods; repositories inside implementation-layer classes join that transaction automatically.
- In service tests that build a `Test.createTestingModule` with repository mocks, add the real readers/calculators to `providers` (they then use the same mocked repositories); mock only refreshers/fetchers and calculators that the test replaces.
- `libs/common` has no `*Service` classes either: nothing there is called by a controller, so its classes use the role names above (`*Fetcher`, `TokenProvider`).

### No circular dependencies

**Circular dependencies are never allowed** — neither between providers (A injects B and B injects A, directly or through a longer chain), nor between modules, nor between files (import cycles). Don't "fix" one with `forwardRef()` / `@Inject(forwardRef(...))` / `ModuleRef`; remove the cycle by moving the shared logic down into the implementation layer (see Layers) that both sides depend on (e.g. `DividendFetcher` fetches/saves dividends and is used by `SecurityRefresher`, which in turn is used by the query-side `DividendService` — dependencies only point one way). If a new class would close a loop, split it instead.

### Entity conventions

- **Column/property names are unprefixed:** `id`, not `userId`; `name`, not `userName`; `email`, not `oauthEmail`. The entity/table already gives the context.
- **Join column naming:** a relation's `@JoinColumn` normally follows the same rule (e.g. `id`). Only when that name would collide with an existing property of the entity that means something different (e.g. the entity has its own `id` and also references `User`), name the join column `<table name> + <property name>` in camelCase — e.g. `@JoinColumn({ name: 'userId' })`.
- **Prices, quantities and money amounts use `@Column(decimalColumn)` with TS type `string`** (`libs/common/src/base/decimal-column.ts`: `DECIMAL(20, 6)`, no transformer — mysql2 returns DECIMAL as a string like `'123.450000'`). Don't use plain `@Column()` (`int`), and never convert them to `number`.
  - **Do all arithmetic with decimal.js** (`import { Decimal } from 'decimal.js'` — the default import doesn't type-check under NodeNext). Accept inputs as `Decimal.Value`.
  - **Before saving, truncate by the security's currency with `truncateByCurrency(value, security.currency)`** (`libs/common/src/security/currency-decimal.ts`): `KRW` (domestic stocks/bonds) → integer, `USD` (overseas) → 6 decimal places, always `ROUND_DOWN`. This applies to both money and quantities. Look the `Security` up in the service to get its currency (see `BalanceService.registerBalance`).
- **Enum columns need `@Column({ type: 'enum', enum: X })`** — a bare `@Column()` on an enum-typed property fails at startup with `Data type "undefined" ... is not supported`.
- **Composite-FK join columns must name their target:** `@JoinColumn([{ name: 'userId', referencedColumnName: 'userId' }, { name: 'securityId', referencedColumnName: 'securityId' }])`. Without `referencedColumnName`, TypeORM mapped both to `userId` (`FOREIGN KEY (userId, userId)`, then `Duplicate column name`).
- **Relations are unidirectional by default.** Declare the relation only on the owning side (the side with the `@JoinColumn`, usually `@ManyToOne`/`@OneToOne`) and omit the inverse `@OneToMany`/inverse-side callback. Add a bidirectional relation only when it is truly unavoidable, and note why in a comment.

### Data access: Repository only

- **All CRUD goes through TypeORM `Repository`**, using its methods (`find*`, `save`, `insert`, `update`, `delete`, ...).
- **Repositories are obtained only by constructor injection with `@InjectRepository`:**
  ```ts
  constructor(
    @InjectRepository(User)
    private readonly userRepository: Repository<User>,
  ) {}
  ```
  The entity must be in a `TypeOrmModule.forFeature([...])` imported by that feature's module. Don't get repositories any other way (`dataSource.getRepository(...)`, `manager.getRepository(...)`, custom repository classes).
- Don't do CRUD via `EntityManager` methods (`manager.save(Entity, ...)`, `dataSource.manager.*`), `createQueryBuilder`, or raw `query()`.
- **Transactions use `@Transactional()` from `typeorm-transactional`** on a service method; injected repositories automatically join the transaction, and a thrown error rolls everything back. Don't use `dataSource.transaction(...)` or `QueryRunner`. Setup (already done): `initializeTransactionalContext()` in `main.ts` before `NestFactory.create`, and `addTransactionalDataSource` in `DatabaseModule`'s `dataSourceFactory` (through `registerTransactionalDataSource`, which first calls `deleteDataSourceByName('default')`: `@nestjs/typeorm` calls the factory again on every connection retry, and a leftover registration made `addTransactionalDataSource` throw `DataSource with name "default" has already added`, hiding the real connection error). Tests that call a `@Transactional()` method against a real DB must call `initializeTransactionalContext()` first.

### TypeORM gotchas in this setup

- `autoLoadEntities` only loads entities passed to some `forFeature()`. Every entity on either side of a relation must be registered, or startup fails with `Entity metadata for X#y was not found`.
- `synchronize: true` alters the live DB schema on every boot from entity definitions — entity changes are schema changes.
- **Per-group sequence numbers (max + 1) are assigned in a Writer, not in entity listeners** (`@BeforeInsert` has no DI and would need a global DataSource + QueryBuilder). In a `@Transactional()` service method, first lock the owning parent row by PK (e.g. `userRepository.findOne({ where: { id }, lock: { mode: 'pessimistic_write' } })`), then read the group's last row with `findOne({ order: { sequence: 'DESC' } })` and save with `+ 1`. Don't put the lock on the sequence table's own range query: InnoDB gap locks make concurrent inserts deadlock (verified — 2 of 5 concurrent saves failed even with 3 retries). A PK lookup on the parent takes a plain record lock, so same-owner saves run one at a time with no deadlock (verified with 10 concurrent saves). See `PurchaseWriter` (`lockOwner` then `append`/`sell`), called from `BalanceService`.
- `Oauth → User` is a unidirectional `@ManyToOne` (`User` has no `oauth` property), so there is no cascade from `User`. Save the `User` first (`userRepository.save`), then save `Oauth` with `user` set (`oauthRepository.save`), in one `@Transactional()` method (see `AuthService.findOrCreateOauthUser`). `Oauth` has a composite PK (`id` = the user's id, doubling as the `@JoinColumn` to `User`, + `type` enum).
- **Changing the PK of a table that a foreign key uses fails in `synchronize`** (`Cannot drop index 'PRIMARY': needed in a foreign key constraint`) — e.g. adding `accountId` to the `UserBalance`/`PurchaseDateBalance` PKs, where the `user_balance.userId → user` FK used the PK as its index and `purchase_date_balance → user_balance` referenced it; a failed boot can also leave half-applied changes (a renamed column keeping its old enum type). Deploy in stages, each its own branch pushed to master: (1) remove the `@ManyToOne`/`@JoinColumn` relations involved (keep ones the code reads with `relations`, e.g. `UserBalance.security` for `GET /balance`, if they don't block the change) and deploy — `synchronize` drops those FKs, then changes the PKs/columns (new PK columns get their `default`); (2) the user inserts the parent rows the new FKs will reference directly in the DB (e.g. `INSERT IGNORE INTO account (userId, id, securityCompany, accountType) SELECT DISTINCT userId, 1, 'SAMSUNG', 'NORMAL' FROM user_balance;`) — push step 3 only as a branch until they confirm; (3) restore the relations and deploy — the FKs are recreated.

## Environment

`.env` (not committed) supplies `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`, `DB_SSL` (`true` in production: the Lightsail managed MySQL has `require_secure_transport=ON`, so `db.config.ts` connects with `ssl` = the `aws-ssl-profiles` AWS RDS CA bundle, verifying the server certificate; leave it unset for a local MySQL without SSL), `PORT`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `API_URL` (the API's public origin, e.g. `http://localhost:8080` locally, `https://api.mudaeng.online` in production) + `GOOGLE_CALLBACK_URI` (path only, `/auth/google/callback`; the Google callback URL is `API_URL + GOOGLE_CALLBACK_URI` and must be registered in Google Cloud Console), `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET` (must differ), `JWT_ACCESS_EXPIRES_IN` / `JWT_REFRESH_EXPIRES_IN` (seconds), `FRONTEND_URL1` / `FRONTEND_URL2` (CORS origins, e.g. `https://www.mudaeng.online` / `https://mudaeng.online`; `FRONTEND_URL1` is also the post-login redirect target), `NODE_ENV` (`production` disables Swagger and makes the refresh cookie `secure`), `HOST` (listen address, default `127.0.0.1`; production runs behind Nginx with `PORT=3000`), `TOSS_CLIENT_ID` / `TOSS_CLIENT_SECRET` (Toss Open API; the calling machine's IP must be on Toss's allowed-IP list, otherwise 403), `MASSIVE_API_KEY` (Massive REST API, sent as `Authorization: Bearer`), `DATA_GO_KR_SERVICE_KEY` (data.go.kr decoding key, sent as the `serviceKey` query param), `KIS_CLIENT_ID` / `KIS_CLIENT_SECRET` (Korea Investment & Securities Open API appkey/appsecret).

### Toss Open API

Call Toss only through `TossClient` (`libs/common/src/client/toss/toss.client.ts`, exported by `TossModule`). It caches the access token in memory until shortly before expiry: Toss allows one valid token per client, so issuing a new one revokes the previous token — never request a token per call. If another process (e.g. a `--run` batch next to the scheduled one) issues a token, a `listStocks` 401 drops the cached token and retries once with a new one. `GET /api/v1/stocks/all` is rate-limited to 1 request/second (the import waits between markets). Only the batch calls Toss: its `domestic-securities` / `overseas-securities` jobs (or `--run=` either) call `SecurityFetcher.importFromToss(markets)`, which upserts the markets' listings into `Security` (`id` = ISIN, currency from the market). The api app has no `POST /securities/import` any more.

### Massive API

Call Massive only through `MassiveClient` (`libs/common/src/client/massive/massive.client.ts`, exported by `MassiveModule`). `ExchangeRateFetcher.importFromMassive` (`@app/common`, input `{ from?, to? }`, default the last 2 years; the batch's `exchange-rates` job) fetches `C:USDKRW` daily bars and upserts them into `DailyExchangeRate` as `currency = USD` (KRW per USD; `date` = the bar's UTC date). Rates keep 6 decimals (`ROUND_DOWN`, `truncateRate`) — don't use `truncateByCurrency` on them, KRW would cut them to integers. The Currencies Basic plan only serves 2 years of end-of-day data.

`UsDailyPriceFetcher.importFromMassive` (`@app/common`, same input; the batch's daily `us-daily-prices` job) calls the Daily Market Summary (`/v2/aggs/grouped/locale/us/market/stocks/{date}`) once per weekday — one call returns every US ticker for that day, holidays return no results — and upserts the bars into `DailySecurity` for `USD` securities, matched by `Security.symbol` (Toss preferred-share symbols `BAC-P` become Massive `BACpP`; unknown tickers are skipped; the conversion is `toMassiveTicker` in `libs/common/src/client/massive/massive-ticker.ts`). Prices use `truncateByCurrency(USD)`.

Security lookup is split in two public (no JWT) routes, because a name can equal another security's symbol (e.g. `SK`): `GET /securities?keyword` (`SecurityService.searchSecurities`) finds securities by exact `symbol`, then exact `name`, then partial `name` (`Like`, `%`/`_`/`\` escaped) — never by ISIN — capped at 20, each with its latest stored closing price (null if none); `GET /daily-securities?securityId&from&to` (`DailySecurityService.getDailyPrices`) then refreshes that security online (`SecurityRefresher.refresh`) and reads the daily bars for that exact ISIN (none → 404). `from`/`to` are optional and inclusive; prices are truncated by the security's currency.

**Purchase exchange rate:** `PurchaseDateBalance.exchangeRate` (nullable, KRW per USD, 6 decimals `ROUND_DOWN` — not `truncateByCurrency`) is the rate the user actually paid. `POST /balance` takes an optional `exchangeRate`: `KRW` securities always store null (input ignored); others store the input, else the latest USD `closingRate` on or before `purchaseDate`, else null (registration still succeeds). `POST /balance/sale` copies it to a split-off sold row and only merges into a sold row with the same `price` **and** `exchangeRate`. Every KRW conversion of a USD purchase cost — `GET /balance` (`krwPurchaseAmount`/`krwAveragePrice`), `GET /balance/purchases`, `GET /balance/returns` — uses the stored rate, falling back to the latest USD rate on or before `purchaseDate` (none → 404 in `/balance` and `/balance/returns`). `PATCH /balance/purchases` (JWT, `BalanceService.updateExchangeRate`, body `{ securityId, purchaseDate, sequence, exchangeRate }`) changes one row's stored rate (sold rows too; `exchangeRate: null` clears it so queries fall back again — the key is required, omitting it is 400); no row → 404, `KRW` security → 400. Evaluation amounts still use the latest rate (`/balance`) or the rate on or before `to` (`/balance/returns`), so FX gains are in the KRW totals.

**Accounts (계좌):** `Account` (`libs/common/src/user/account.entity.ts`, table `account`, composite PK `userId` + `id` = per-user sequence, `securityCompany` (`SecurityCompany` enum, `libs/common/src/user/security-company.enum.ts`, Korean brokers + `ETC`) and `accountType` (`AccountType` enum: `NORMAL`·`ISA`·`IRP`·`PS`)) is the account a purchase belongs to. Relations: `PurchaseDateBalance → UserBalance → Account → User` — `UserBalance` (PK `userId` + `accountId` + `securityId`) and `PurchaseDateBalance` (PK `userId` + `accountId` + `securityId` + `purchaseDate` + `sequence`) both carry `accountId`; `PurchaseDateBalance` has no broker column any more. `sequence` is still numbered per (user, security, purchaseDate) **across accounts** (`PurchaseWriter.saveWithNextSequence`), so `securityId` + `purchaseDate` + `sequence` still identifies one row and the sell/delete/patch APIs keep that key. The feature lives in `apps/api/src/user/` (`UserModule`, exports `AccountReader`/`AccountWriter`, imported by `BalanceModule`): `GET /accounts?securityCompany` (JWT, `AccountService.getAccounts`) → `{ accounts: [{ id, securityCompany, accountType }] }` (id order; omitted = all accounts), `POST /accounts` (JWT, 201, `AccountService.createAccount`, body `{ securityCompany, accountType? }` — omitted type = `NORMAL`; `@Transactional()`: `AccountWriter.lockOwner` locks the `User` row, then `AccountWriter.create` saves id = the user's max + 1) → `{ id, securityCompany, accountType }`, `PATCH /accounts/:id/type` (JWT, body `{ accountType }`; not the user's → 404), `DELETE /accounts/:id` (JWT, 204, `AccountService.deleteAccount`; not the user's → 404; any `PurchaseDateBalance` row of that account, sold ones included (`AccountReader.hasPurchases`, which is why `UserModule` registers `PurchaseDateBalance`) → 400 — the FKs cascade, so deleting would wipe the history; move rows with `PATCH /balance/purchases/account` or delete them first). Writes also create accounts on their own: `AccountWriter.resolve(userId, securityCompany, accountId?)` picks the account for writes — the given `accountId` (not the user's → 404, other broker → 400), else the user's first account of that broker (id order), else it **creates a `NORMAL` account** (`create`, id = the user's max + 1; call it after `PurchaseWriter.lockOwner`). `POST /balance` takes `securityCompany` (required) + optional `accountId`; `POST /balance/sale` keeps the source row's account and only merges into a sold row of the same account (and price/rate); `POST /balance/sale/bulk` (`{ securityId, securityCompany, accountId?, amount, saleDate }`) sells LIFO (newest purchase first, `PurchaseWriter.sellLifo`) from that account's unsold rows bought on or before `saleDate`; held total < amount → 400 with nothing sold. The query filters are an optional `accountId` (query string, coerced to a positive int): `GET /balance`, `/balance/purchases`, `/balance/monthly`, `/balance/dividends`, `/balance/returns`, `/balance/dividend-metrics` (passed on to `DividendHistoryCalculator.calculate` / `PurchaseReader.findByUser`); omitted = all accounts. `GET /balance` reads `UserBalance` per account, so it keeps one row per security (`uniqueBySecurity`). `PATCH /balance/purchases/account` (JWT, `BalanceService.updatePurchaseAccount`, body `{ securityId, purchaseDate, sequence, accountId }`) moves one row to another of the user's accounts (sold rows too, no merge/split, sequence unchanged; `PurchaseWriter.moveAccount` uses `update` because `accountId` is part of the PK, creates the target `UserBalance` and deletes the source one when it empties) — use it for transfers to another broker. `PurchaseWriter.remove` / `removeByAccount` delete the `UserBalance` of that account only.

**Toss import:** `POST /balance/toss` (JWT, 201, `BalanceService.bulkRegisterToss`, body `restapi/dto/bulk-register-balance-toss.schema.ts` = `{ accountId?, transactionList, confirmedTransfersOut? }`) rebuilds one Toss account in one `@Transactional()`: the account is `AccountWriter.resolve(userId, TOSS, accountId)` (first Toss account, or a new `NORMAL` one), `PurchaseWriter.removeByAccount` deletes all its rows and `UserBalance`s, then all buys (`BUY` + remaining `SECURITIES_TRANSFER_IN`) are appended oldest date first, then all sells (`SELL` + confirmed `SECURITIES_TRANSFER_OUT`) are processed oldest sale first, each by `PurchaseWriter.sellLifo` (newest purchase first; held < quantity → 400 and everything rolls back). **Stock lending (주식 빌려주기):** lending out shows up as `SECURITIES_TRANSFER_OUT` and the return as `SECURITIES_TRANSFER_IN`, with no field telling them apart from real transfers, so `offsetTossLending` (`balance/toss-lending.ts`) runs per ISIN in settlement date → transaction time order: a transfer out is treated as lent (not sold) unless its key is in `confirmedTransfersOut`; a later transfer in first pays back the oldest outstanding lent quantity (partial returns too) and only the excess is bought (at the stored close). Offset items go to `skipped` (`빌려주기 반환`, `빌려주기 출고(반환됨)`); outstanding lent transfers come back in `lentTransfers` (`{ key, remainingQuantity }`). Key = `{ isinCode, settlementDate, quantity, index }` (index = order among transfers out with the same ISIN/date/quantity, by transaction time; quantity normalised so `10` = `10.000000`). The client sends a key back in `confirmedTransfersOut` when that transfer out really left (it is then sold LIFO). The response also has `accountId`. The type lists are `BUY_TYPES` / `SELL_TYPES` at the top of `balance.service.ts`. Security = `isinCode` (`Security.id`). Buys: `amount = quantity`, `price = filledPrice` (`truncateByCurrency`), **no daily-price/range check**, exchange rate = the item's `exchangeRate`, else the USD rate on or before the date (KRW → null). Transfers in (event/fractional-share grants, stock dividends, moves from other brokers) have no `filledPrice`, so the price is the latest stored close on or before the trade date (`DailyPriceReader.findLatestOnOrBefore`, one query per transfer) — for shares moved from another broker this is not the real cost; no close → skipped (`입고일 시세 없음`). Trade date (`balance/toss-trade-date.ts`): Toss's `settlementDate` is 2 trading days after the real fill, so every trade (KR and US) is dated `settlementDate` − 2 KRX trading days (`krwTradingDayBefore`, `security/trading-day.ts`); `transactionTime`/`marketCountry` are not used for the date. Trading days come from one `DailyPriceReader.findKrwTradingDays(min settlementDate − 14 days, max settlementDate)` call; when they don't cover a date, weekdays are counted instead. Cancellations, unknown/null ISINs (e.g. option expiries, which have no ISIN) and items without quantity (or a `BUY` without `filledPrice`) are skipped and listed in `skipped` with a reason; other types (`DEPOSIT`, `DIVIDEND` …) are ignored. Enum fields in the schema accept unknown strings (Toss may add values). No `SecurityRefresher` call. A full Toss history exceeds Express's default 100kb JSON limit (413), so `main.ts` sets `app.useBodyParser('json', { limit: '1mb' })`.

`GET /balance/purchases?securityId` (JWT, `BalanceService.getPurchases`) lists the user's `PurchaseDateBalance` rows for one security, newest `purchaseDate` first (then `sequence` desc), sold rows included, with the purchase exchange rate (stored rate with `exchangeRateDate` null, else the fallback rate and its date; null for KRW). `price` is cut to 2 decimals (`ROUND_DOWN`) in the response. The response also has `amount` (total held quantity = unsold rows only, after the `accountId` filter) and `accountAmounts` (`[{ accountId, securityCompany, accountType, amount }]` per account, unsold rows only, accounts with quantity > 0, account id order; `accountAmountsOf` in `balance/account-amount.ts`). Each item has `accountId`, `securityCompany`, `accountType`. Each `GET /balance` item has the same `accountAmounts` next to its total `amount`.

`DELETE /balance/purchases?securityId&purchaseDate&sequence` (JWT, 204, `BalanceService.deletePurchase`) deletes one mis-registered `PurchaseDateBalance` row of the user (sold rows too; none → 404). `sequence` is only unique within a `purchaseDate`, so all three are required. When the security has no rows left, its `UserBalance` is deleted too. Other rows' sequences are not renumbered.

`MassiveClient.getDividends(ticker, fromExDate, toExDate)` reads `/stocks/v1/dividends` (cash dividends, filtered by ex-dividend date, `limit=5000`, follows `next_url`). `DividendFetcher` uses it for `USD` securities (see KIS Open API below). `MassiveClient` retries a 429 after `Retry-After` (default 15s), so a rate-limited plan just runs slower.

### data.go.kr

Call data.go.kr only through `DataGoKrClient` (`libs/common/src/client/data-go-kr/data-go-kr.client.ts`, exported by `DataGoKrModule`). `getStockPrices` (FSC stock price API `getStockPriceInfo_V2`, domestic listed stocks only) and `getEtfPrices` (FSC securities product price API `GetSecuritiesProductInfoService_V2/getETFPriceInfo_V2`; the stock API has no ETFs) share the query and response shape through `getPricePage`. Only `DomesticDailyPriceFetcher` (`@app/common`; batch `domestic-daily-prices`) uses them, for all securities at once (no `isinCd`). `endBasDt` is exclusive, so callers pass `to + 1 day`. Errors such as an unregistered key come back as `OpenAPI_ServiceResponse` (or XML) instead of `response.header`, and the client turns them into 502. The data.go.kr key needs a separate 활용신청 for 증권상품시세정보 for ETFs; otherwise the call returns `SERVICE_KEY_IS_NOT_REGISTERED_ERROR`.

### KIS Open API

Call KIS (한국투자증권, `https://openapi.koreainvestment.com:9443`) only through `KisClient` (`libs/common/src/client/kis/kis.client.ts`, exported by `KisModule`). The access token (`POST /oauth2/tokenP`) is stored in `ClientToken` (`clientType = KIS`; `token` is `text` because the JWT is longer than 255 chars) and reused across calls and restarts — never issue one per call. `KisClient` issues a token only when none is stored, or once when a call returns 401 (KIS may also report an expired token as HTTP 500 with `msg_cd` `EGW00121`/`EGW00123`), saves it, and retries that call once (shared by every call through `withToken`).

Domestic daily prices (`KisClient.getDailyPrices(symbol, fromYmd, toYmd)`) use 국내주식기간별시세 (`GET /uapi/domestic-stock/v1/quotations/inquire-daily-itemchartprice`, `tr_id` `FHKST03010100`, `FID_COND_MRKT_DIV_CODE=J` for stocks and ETFs, `FID_PERIOD_DIV_CODE=D`, `FID_ORG_ADJ_PRC=1` = unadjusted, matching data.go.kr; max 100 rows). A day without prices comes back as one empty object in `output2`, which the client drops.

Dividends for `KRW` securities come from the KSD dividend schedule (`GET /uapi/domestic-stock/v1/ksdinfo/dividend`, `tr_id` `HHKDB669102C0`, per 6-digit `Security.symbol`); `USD` securities use Massive Dividends with `toMassiveTicker(symbol)` (amount `truncateByCurrency(USD)`, `noticeDate` = record date, or ex-dividend date if missing; `exDividendDate` = Massive's ex-dividend date, or the record date if missing — the US settles T+1 so they are the same day). `DividendFetcher.fetchAndSave(security, from, to)` (`security/dividend.fetcher.ts`) upserts `Dividend` (cash → `MONEY`; KIS stock dividends → `STOCK`, rate in %; rows without a payment date are skipped since it is part of the PK).

KIS overseas dividend APIs were checked (2026-11, KO/O) and are **not** used: 해외주식 기간별권리조회 (`/uapi/overseas-price/v1/quotations/period-rights`, `CTRGT011R`, `RGHT_TYPE_CD=03`) returns per-share cash dividends back to ~2017 complete (older years have gaps; 100 rows/page, `tr_cont` paging) but has **no payment date** (only `bass_dt`/`acpl_bass_dt`) and lags new announcements; 해외주식 권리종합 (`rights-by-ice`, `HHDFS78330900`) has ex/record/payment dates but no amount and only ~4 years. Since `paymentDate` is part of the `Dividend` PK, mixing them with Massive rows would duplicate dividends, so USD history stays at Massive's 2 years.

**Ex-dividend date (`Dividend.exDividendDate`, nullable):** KIS gives only the record date, so `DividendFetcher` computes the KRW ex-dividend date with `krwExDividendDate(recordDate, tradingDays)` (`security/ex-dividend-date.ts`, = `krwTradingDayBefore(recordDate, 1, …)` from `security/trading-day.ts`, shared with the Toss import): Korea settles T+2, so it is the trading day before the last trading day on or before the record date (record date 2024-12-31, a market holiday → last trading day 12-30 → ex-date 12-27). Trading days come from `DailyPriceReader.findKrwTradingDays(from − 14 days, to)` — the dates of the stored Samsung Electronics prices (`KRW_CALENDAR_SECURITY_ID`, read through the PK instead of a DISTINCT over every security), loaded once per fetch and only when KIS returned rows. When the list doesn't cover the record date (latest trading day before it, e.g. a future record date, or the list starts less than 7 days before it) it falls back to weekdays only. The refresh re-fetches the last year every day and upserts, so a weekday fallback is corrected once the prices exist. Rows saved before the column existed stay null until re-fetched; to backfill, run `UPDATE security_search SET fromDate = NULL WHERE type = 'INCOME';` once — each security then re-fetches its full range on its next refresh (USD only goes back 2 years, older USD rows stay null).

**Online refresh:** `SecurityRefresher.refresh(security)` (`security/security.refresher.ts`, exported by `SecurityModule` with `DailyPriceReader` and `ExchangeRateReader`) is how query APIs get fresh data — call it, never the clients or `DividendFetcher`/`DailyPriceFetcher` directly. `SecuritySearch` has a composite PK (`id`, `type`: `SearchType.INCOME` = dividends, `SearchType.PRICE` = daily prices), each row with its own `lastSearchDate`.
  - **Dividends (`INCOME`), at most once a day:** a row whose `lastSearchDate` is today (Asia/Seoul) is skipped; otherwise dividends fetch from the start date → 1 year ahead (`KRW` start = `KRW_DIVIDEND_START` `2000-01-01`, as far back as the KIS dividend schedule goes; `USD` = 2 years back, the Massive Basic limit). Incremental: the row also stores `fromDate`, the start of the range already loaded. When `fromDate` is on or before the start date, only `lastSearchDate − 1 year` onward is fetched (never before the start date) and `fromDate` is kept; otherwise (no row, `fromDate` null from before the column existed, or later than the start) the full range is fetched and `fromDate` = start. Moving the start date earlier therefore re-fetches the full range once per security.
  - **Domestic prices (`PRICE`, `KRW` only), one day:** the bulk comes from the batch's `domestic-daily-prices` job; the refresher only tops up one day from KIS. The target date is `krwPriceDate()` (`libs/common/src/base/iso-date.ts`): yesterday before 15:30 KST (`KRW_MARKET_CLOSE`, today's bar isn't final yet), today from 15:30. If the `PRICE` row's `lastSearchDate` is already that date, skip; else if `DailyPriceReader.findOn(id, date)` finds a stored bar, no call; else `DailyPriceFetcher.fetchAndSave(security, date)` (`security/daily-price.fetcher.ts`, KIS `getDailyPrices` by `symbol`, `truncateByCurrency(KRW)`; a holiday saves nothing). On success the row is upserted with `lastSearchDate` = that date (`fromDate` untouched), so a holiday isn't asked again the same day.
  - `USD` prices are never fetched online — the batch's `us-daily-prices` job loads every US ticker daily — so a `USD` refresh is one Massive dividends call and has no `PRICE` row. Each kind's row is upserted (`['id', 'type']`) only when that kind succeeds; a failure is logged, never thrown, so the caller answers from stored data and the next call retries just that kind. Other currencies are ignored. Concurrent refreshes of the same security share one in-flight promise (`inFlight` map, keyed by ISIN, removed when it settles), because the `lastSearchDate` row is only written after the external call — without it, a page firing several query APIs at once called Massive once per request and hit 429. Callers: `GET /daily-securities`, `GET /balance/dividends` (each held security, sequentially — Massive rate limits can make a first call of the day slow with many USD securities; `/balance/returns` gets it through `DividendHistoryCalculator`), and `BalanceService.registerBalance` (only after the `saveBalance` transaction has committed, so a failed registration never calls external APIs). KIS issues at most one token per minute (`EGW00133`). Reuse it for future security lookup APIs instead of calling `KisClient` directly.

### Dividend history

`GET /balance/dividends?from&to` (`DividendHistoryService.getDividendHistory` → `DividendHistoryCalculator.calculate`, `balance/dividend-history.calculator.ts`, `balance/restapi/dividend-history.*`) first refreshes each security the user has held (`SecurityRefresher.refresh`), then reads stored `Dividend` rows. Rules: cash dividends (`MONEY`) only; `from`/`to` filter `paymentDate` (inclusive; omitted = unbounded, so announced future payments are read too) and months group by payment month; only items paid by today (Asia/Seoul, `todayInSeoul`) go into `months`/`total` — items with `paymentDate` after today come back separately in `scheduled` (`{ total, items }`, same summary/item shape), so `/balance/returns` and `/balance/monthly`, which read `months` only, never count unpaid dividends; quantity = sum of the user's `PurchaseDateBalance` rows (sold ones included) entitled to the dividend (`entitledQuantity`): with an `exDividendDate`, `purchaseDate < exDividendDate` and (`saleDate` null or `>= exDividendDate`) — bought by the day before the ex-date, sold on or after it; rows without one (saved before the column) fall back to `purchaseDate <= noticeDate` and (`saleDate` null or `> noticeDate`). Rows with quantity 0 are dropped; each item carries `noticeDate` and `exDividendDate` (nullable); amount = per-share × quantity, `truncateByCurrency`. USD converts with the latest USD `closingRate` on or before `paymentDate` (`krwAmount` null and left out of the sums if none). Monthly/total sums add the truncated per-row values. **After tax:** every item also has `taxAmount`, `afterTaxAmount` (security currency), `afterTaxUsdAmount` (null for KRW) and `afterTaxKrwAmount` (USD × the same payment-date rate, null without one), and every summary has `afterTaxKrwAmount`/`afterTaxUsdAmount`/`afterTaxUsdKrwAmount`/`afterTaxTotalKrwAmount`. Tax = per-share × the entitled quantity held in taxed accounts × the rate, truncated by currency (`balance/dividend-tax.ts`: only `NORMAL` accounts are taxed — KRW 15.4%, USD 15% US withholding; ISA·IRP·PS pay nothing on receipt, so after tax = pre-tax; ISA maturity / pension withdrawal taxes and the 10-won truncation of Korean withholding are not modelled). The calculator reads the account types with `AccountReader.findByUser`.

`GET /balance/dividend-metrics?accountId` (JWT; `DividendMetricsService`, `balance/restapi/dividend-metrics.*`) returns pre-tax dividend metrics for the positions held today (unsold rows, account filter like the others): per security (ISIN order, with `symbol`) `trailingPerShare`/`paymentCount` = cash dividends per share paid in (today − 1 year, today], `previousPerShare` = the 12 months before that, `growthRate` = trailing / previous − 1 (null when previous is 0), with `previousPaymentCount` and `growthBasis`: `TOTAL` normally, `PER_PAYMENT` = per-payment averages (trailing / paymentCount ÷ previous / previousPaymentCount − 1), `KRW` securities only, when the previous window has fewer payments than the trailing one **and** the security has no `MONEY` dividend paid on or before `previousFrom` (`dividendRepository.existsBy`, only queried in that case) — i.e. listed inside the previous window, whose partial year would inflate the sum ratio (e.g. 7 vs 12 monthly payments → +83% instead of +6.79%). `USD` always uses `TOTAL`: its dividends are only stored for 2 years, so the listing date is unknown, and an old US security that switched from quarterly to monthly payments would show a large false drop per payment; with equal counts both methods agree, `annualDividend` = trailing × quantity (security currency) and `krwAnnualDividend` (USD × the latest rate on or before today; missing rate → 404), `krwPurchaseAmount` (USD at each purchase's own rate, as in `/balance/returns`), latest `closingPrice`/`priceDate`/`krwEvaluationAmount` (null without a price), `yieldOnCost` = KRW annual dividend / KRW cost, `currentYield` = trailing per share / latest close. `total` sums the truncated items; its `currentYield` uses only securities with a price. Percentages use `percentOf` (`balance/return-rate.ts`, 2 decimals `ROUND_DOWN`, null when the base is 0). It refreshes each held security first (`SecurityRefresher`, sequential) and reads the last 24 months of `MONEY` dividends in one query.

`GET /balance/returns?from&to` (both optional — omitted `from` = the whole history, so every purchase row uses its cost as `baseAmount` and dividends count from the beginning; omitted `to` = today (Asia/Seoul); the response `from` is null when omitted and `to` is always the valuation date used; `PeriodReturnService`, `balance/restapi/period-return.*`) values the positions held on `to` (`purchaseDate <= to`, `saleDate` null or `> to`; sale prices aren't stored, so sold positions only count through their dividends) at the latest closing price on or before `to`, and adds dividends from `DividendHistoryCalculator` for the same `from`/`to`. USD cost in KRW uses each purchase's own rate (the stored purchase exchange rate, else the latest USD rate on or before `purchaseDate`, so FX gains are in the KRW return); USD evaluation uses the latest rate on or before `to`. **Profit is a period return against `baseAmount`, not the cost:** per purchase row, `purchaseDate < from` → the latest close on or before `from` × quantity (USD × the latest rate on or before `from`, top-level `startExchangeRate`), falling back to the cost when that close is missing or older than `purchaseDate` (or no USD start rate); `purchaseDate >= from` → the cost. `purchaseAmount` (real cost) stays in the response; `profit`/`returnRate` and the after-tax ones use `baseAmount` (evaluation items: `krwBaseAmount`/`usdBaseAmount`, `startClosingPrice`/`startPriceDate` when a start close was used). E.g. 1 share bought at 40,000, close 190,000 on 11-22 and 140,000 on 11-23: `from=11-22&to=11-23` → −50,000; whole history → +100,000. Close lookup dates come from `priceLookupDate(currency, date)` (`security/price-date.ts`, shared with `/balance/monthly` and `/balance/dividend-metrics`): KRW closes are looked up only up to `krwPriceDate()` (`libs/common/src/base/iso-date.ts`), so before 15:30 KST a `to`/`from` of today uses the previous close; USD closes are looked up one day earlier (`from − 1`, `to − 1`): bars are stored by US trading date, and US day D closes on the morning of D+1 KST, so on Korean date X the latest closed US day is X − 1 (`from`=yesterday, `to`=today → last night's US session; before the 14:30 batch it is 0, like KRW before 15:30). Securities = held on `to` ∪ paid a dividend in the period. `returnRate` lives in `balance/return-rate.ts` (shared with `BalanceService`). The pre-tax fields stay as they were; after-tax ones are added next to them: dividend items/total `afterTaxUsdAmount`/`afterTaxKrwAmount`, total items/total `afterTaxDividendAmount`, `afterTaxTotalAmount` (evaluation + after-tax dividends), `afterTaxProfit`, `afterTaxReturnRate`. `/balance/monthly` and `/balance/dividend-metrics` stay pre-tax.

`GET /balance/monthly?from&to` (both `YYYY-MM`, required, `to` at most the current month, ≤ 120 months; `MonthlyBalanceService`, `balance/restapi/monthly-balance.*`) returns, oldest month first, each month's `total` and per-security `items` of `purchaseAmount`, `evaluationAmount`, `dividendAmount` and `totalAmount` (= evaluation + dividends), all KRW. The valuation date is the month's last day, or today (Asia/Seoul) for the current month. Held positions, KRW cost (stored purchase rate, else the rate on or before `purchaseDate`), evaluation (latest close and USD rate on or before the date — USD closes on or before the date − 1, the last US trading day closed by then; missing → 404) follow `/balance/returns`. `dividendAmount` is **cumulative from the beginning** — every dividend paid on or before the date, including before `from`, from one `DividendHistoryCalculator.calculate(user, { to: lastDate })` call (which also does the online refresh); `krwAmount` null is left out. Items = held on the date ∪ any dividend paid by then, so a sold security stays with quantity 0 and its dividends. Prices and rates are loaded once up to the last date and looked up in memory (binary search), not queried per month.

### Auth flow

1. `GET /auth/google` → Google → `GET /auth/google/callback`: the handler takes the Google user with `@GoogleUser()` (`auth/restapi/google-user.decorator.ts`, the `User` returned by `GoogleStrategy.validate`) and `AuthService.loginWithOauth` saves both tokens as a **new** `Token` row (one row per login session/device — auto-increment `id`, `userId` → `User` — so logging in on a phone keeps the PC logged in; it first deletes this user's rows not updated for `JWT_REFRESH_EXPIRES_IN`, since there is no logout endpoint), sets the refresh token as an httpOnly `refreshToken` cookie (`path: /auth`), and returns `{ url: ${FRONTEND_URL1}/auth/callback }` for `@Redirect()`.
2. Frontend calls `POST /auth/access` with credentials: `AuthService.issueAccessToken` looks the refresh token up in `Token` and returns a new access token in the body (also stored in `Token`); the refresh token is unchanged.
3. Frontend sends `Authorization: Bearer <accessToken>`; protect routes with `@UseGuards(AuthGuard('jwt'))` (`JwtStrategy`, access secret) and take the user with the `@CurrentUser()` param decorator (`auth/restapi/current-user.decorator.ts`, gives `AuthUser` = `{ id, rules }`) instead of `@Req()`, passing it to the service (e.g. `GET /auth/me` → `AuthService.getMe`). An expired access token gets 401.
4. On 401, frontend calls `POST /auth/reissue` with credentials: `AuthService.reissueTokens` looks the refresh token up in `Token` (missing, or `userId` ≠ the token's `sub` → 401), replaces that row's access + refresh pair in place (other devices' rows untouched), resets the `refreshToken` cookie, and returns `{ accessToken }`. The old refresh token is unusable afterwards (rotation).

**Refresh-token context** (`auth/restapi/refresh-token.context.ts`, holding `RefreshTokenContext` + `RefreshTokenContextMiddleware` because the middleware must open the file-private `AsyncLocalStorage`): the middleware opens a per-request store (applied to all routes in `AuthModule.configure`). `@UseGuards(RefreshTokenGuard)` (`auth/restapi/refresh-token.guard.ts`) reads the `refreshToken` cookie, verifies it (missing/expired/invalid → 401), and stores the token and its `sub` (user id). Services then read them with `RefreshTokenContext.getRefreshToken()` / `getSub()` instead of taking them as parameters, and set the cookie with `RefreshTokenContext.setRefreshTokenCookie(token)`. `AuthModule` exports `RefreshTokenContext` and `RefreshTokenGuard` for other feature modules.

Changing `Token`'s PK/columns with existing rows breaks `synchronize` (e.g. the move from one-row-per-user added `userId` NOT NULL → existing rows got 0 → FK failure, app won't boot): empty `token` first (`DELETE FROM token;`, everyone logs in again once). An emptied table recovers even after a failed boot.

**Keep `/auth/access` and `/auth/reissue` as separate endpoints** — don't merge them or remove `/auth/access`. `/auth/access` is only for right after login (new access token, refresh token unchanged); `/auth/reissue` is for an expired access token (both tokens rotated).

**User rules (roles) and admin API:** `UserRule` (`libs/common/src/user/user-rule.entity.ts`, table `user_rule`, composite PK `id` (= User id, FK cascade) + `rule` enum `Rule.USER`/`Rule.ADMIN`) holds a user's roles. `AuthService.findOrCreateOauthUser` saves a `USER` row for every new Google user in the same transaction as `User`/`Oauth`; users created before this have no rows (rules `[]`). `TokenProvider.createAccessToken` reads the user's `UserRule` rows and signs `{ sub, rules }` (refresh tokens carry only `sub`), so `AuthUser` is `{ id, rules }` (`rules ?? []` for older tokens) and role changes apply from the next `/auth/access` or `/auth/reissue`. Admins are granted only in the DB: `INSERT INTO user_rule (id, rule) VALUES (<userId>, 'admin');`. `AdminModule` (`apps/api/src/admin/`, an exception to the entity-domain folder rule: it gathers admin features) protects its controller with `@UseGuards(AuthGuard('jwt'), AdminGuard)` — `AdminGuard` (`admin/restapi/admin.guard.ts`) throws 403 unless `req.user.rules` includes `admin`. `GET /admin/batch-histories?name&status&limit` (`AdminService.getBatchHistories`, `limit` 1–100, default 20) returns `BatchHistory` rows newest `startedAt` first. `GET /admin/security-searches/price` (`AdminService.getPriceSearches`) returns every `SecuritySearch` row with `type = PRICE` as `[{ securityId, name, lastSearchDate, createdAt, updatedAt }]`, newest `lastSearchDate` first (then `securityId`); `SecuritySearch` has no relation to `Security`, so names come from a second `find` by `In(ids)` (`name` null if the security is missing). `GET /admin/client-tokens` (`AdminService.getClientTokens`) returns `[{ clientType, updatedAt }]` from `ClientToken`, newest `updatedAt` first — never the token itself (`select` excludes it); `updatedAt` changes only when a token is issued and saved (`KisClient`), not on every call that reuses it.

**Rate limiting** (`@nestjs/throttler`): `ApiModule` registers `ThrottlerModule.forRoot(THROTTLER_OPTIONS)` and a global `ThrottlerGuard` (APP_GUARD — infrastructure like `DatabaseModule`, so it sits in `ApiModule`). Limits live in `apps/api/src/rate-limit.ts`: 100 req/min per IP by default, `@Throttle(AUTH_THROTTLE)` (10/min) on `/auth/google`, `/auth/google/callback`, `/auth/access`, `/auth/reissue`, `@Throttle(PRICE_THROTTLE)` (30/min) on `GET /daily-securities` (public and triggers external refreshes). Over the limit → 429. The tracker is `req.ip`, which is the real client IP only because of `trust proxy 1` in `main.ts`. Storage is in memory (one pm2 process).

**Google OAuth state** (login CSRF protection): `GoogleStrategy` passes `store: new OAuthStateStore()` (`auth/restapi/oauth-state.store.ts`). There is no express-session, so the state goes in an httpOnly `oauthState` cookie (`path: /auth/google`, 10 min, SameSite=Lax so it rides the top-level redirect back from Google); `verify` compares it with the `state` query in constant time and clears it, mismatch → 401. passport picks the call shape by method arity, so keep `store(req, cb)` at 2 and `verify(req, state, cb)` at 3 parameters (hence the `as unknown as StateStore` cast).

JWTs are signed only through `TokenProvider` (`libs/common/src/auth/token.provider.ts`, from `TokenModule`, which `AuthModule` imports and re-exports so `RefreshTokenGuard` resolves in other modules), which passes the access/refresh secret per call (`JwtModule.register({})` has no default secret). A Google OAuth `client_secret_*.json` sits untracked at the repo root — never commit it.
